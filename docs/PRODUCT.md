## 2. 产品定位与目标

### 2.1 用户问题

以下是本项目的需求假设，需要后续通过试用验证：

1. 用户知道预算与用途，但不熟悉参数，难以把“安静、便携、适合写代码”等需求转为筛选条件。
2. 同一产品存在多个版本，容易混淆价格、轴体、连接方式和实际特点。
3. 通用推荐文章难以同时满足个人预算和具体使用环境。
4. 用户得到推荐后，仍需要知道为什么适合、缺点是什么，以及与其他方案的区别。

### 2.2 产品目标

第一阶段帮助用户完成一次有依据的选购决策：

**描述需求 → 补充必要信息 → 获得推荐 → 比较方案 → 调整并选择。**

推荐应回答四个问题：

- 我可以选哪些具体产品或组合？
- 为什么它们符合我的预算和用途？
- 各方案的差异与取舍是什么？
- 哪些信息有资料支持，哪些仍不确定？

### 2.3 第一版成功的定义

- 无须登录即可走完选购流程。
- 推荐能够对应用户的预算、品类、用途和明确要求。
- 产品版本、参考价和关键参数可以追溯到资料记录。
- 用户能在同一流程内修改需求，查看更新后的结果。
- 资料不足、没有匹配、服务失败时，都有明确说明和下一步操作。

业务效果尚无基线。第一版不预设已实现的转化率、用户规模、推荐准确率或商业收入。

## 3. 目标用户与典型场景

### 3.1 优先用户

[建议] 优先服务有明确预算、希望快速完成选择的普通消费者，包括学生、办公用户与轻度游戏用户。先不以发烧友改装、专业竞技设备调校或企业采购为主要场景。

### 3.2 典型场景

| 场景 | 用户表达 | 应重点理解的信息 |
|---|---|---|
| 宿舍写代码与偶尔游戏 | “500 元买一套键鼠，宿舍用，想安静点。” | 总预算、噪声要求是否必须、连接需求 |
| 办公与表格输入 | “300 元以内的键盘，经常做表格。” | 是否需要数字区、连接设备、布局偏好 |
| 便携鼠标 | “200 元买鼠标，带去上课，电脑接口少。” | 便携偏好、蓝牙或接收器、设备兼容 |
| 已有初步偏好 | “只要无线，不要没有数字区的键盘。” | 明确要求作为约束，不由系统擅自改动 |
| 看完方案后调整 | “这套太贵，预算降到 350，游戏优先。” | 修改预算与优先级，继承未改变的需求 |

以上为设计场景，不是已经开展的用户访谈或调研结论。

## 4. 版本范围与优先级

### 4.1 第一版必须完成（P0）

| 模块 | 范围 | 完成标准 |
|---|---|---|
| 需求输入 | 预算、目标品类、主要用途、自然语言补充 | 支持键盘、鼠标、键鼠组合 |
| 需求理解与确认 | 提取条件、展示理解结果、必要追问 | 用户能看到并修改系统理解的条件 |
| 商品资料 | 精选商品、具体版本、参数、来源与参考价 | 推荐使用经过核对的有效记录 |
| 推荐方案 | 单品或组合、总参考价、理由、取舍 | 返回最多 3 套有实际差异的匹配方案 |
| 方案对比 | 按预算、用途与关键参数比较 | 同类对比，区分键盘与鼠标参数 |
| 继续调整 | 修改预算、用途、品类或偏好 | 主动确认后更新推荐，不丢失上一版结果 |
| 依据展示 | 参数来源、判断依据、价格记录时间 | 用户能查看关键结论的资料出处 |
| 异常处理 | 信息不足、无匹配、过期价格、生成失败 | 不伪造结果，提供可执行的下一步 |

### 4.2 第一版之后增强（P1）

- 收藏方案与查看历史需求。
- 分享可查看的推荐结果。
- 针对“为什么不推荐某型号”的进一步解释。
- 推荐帮助程度反馈，用于识别资料与规则问题。
- 商品维护的可视化管理界面。
- 数据增长后的语义检索与更完整的评测看板。

P0 的资料维护允许使用受控表格或数据文件导入，不要求先开发完整管理后台。

### 4.3 后续商城能力

[后续] 账号体系、购物车、订单、支付、发货、售后、商家权限与自营库存管理。

第一版的销售渠道链接只是站外核对和购买入口。站内不承诺成交、库存预留、最低价或实时到手价。

## 5. 页面与交互设计要求

### 5.1 首页／需求输入

页面首先解释产品能做什么，并提供示例需求与输入入口。

| 输入项 | 要求 | 处理规则 |
|---|---|---|
| 想买什么 | 必填，主动选择 | 键盘、鼠标或键鼠组合 |
| 预算 | 必填，正数，人民币 | 键鼠组合时明确提示为两件商品的总预算 |
| 主要用途 | 必填 | 支持办公、写代码、游戏、便携等；多用途时确认优先级 |
| 补充描述 | 可选 | 用自然语言描述噪声、连接、布局、设备等要求 |
| 其他偏好 | 可选 | 不要求用户先填写专业参数表 |

表单输入与自由描述共同组成一份需求。两者冲突时提示用户确认，不静默覆盖。

预算只限制推荐商品的参考价合计。运费、未核对优惠和其他附加费用未纳入时，需在结果中明确说明。

示例：“预算 500 元，键盘加鼠标，主要写代码，偶尔游戏，宿舍用，希望安静一点。”

### 5.2 需求确认与补充

展示系统理解的简短摘要，例如：“总预算 500 元；键鼠组合；写代码优先；希望降低噪声。”

追问只针对会影响筛选的关键缺失或冲突信息，每轮最多 1～2 个问题。已能形成有效候选时，不强制把所有偏好补齐。

- “需要数字小键盘吗？”适用于布局影响工作用途时。
- “无线是必须，还是有线也可以？”用于区分硬要求与偏好。
- 鼠标的手型、握持方式等只在影响当前候选选择时询问，允许选择“不确定”。

用户应能修改摘要中的条件，并主动点击“查看推荐”。进入页面、刷新或修改输入框均不自动触发新一次推荐。

### 5.3 推荐结果

默认展示最多 3 套方案。有 1～2 套符合要求时按实际数量展示，不为凑数放宽要求或复制相同方案。

每套方案至少包含：

1. 简短的方案定位，依据真实差异命名，例如“更便携”或“保留数字区”。
2. 商品品牌、型号与具体版本；组合中分别列出键盘和鼠标。
3. 每件商品参考价、组合总参考价、价格渠道与记录时间。
4. 与用户需求相关的关键参数。
5. 2～3 条有依据的推荐理由。
6. 主要取舍、信息缺口与尚不能确定的结论。
7. “对比方案”“查看依据”“调整需求”等操作。
8. 有可信对应渠道时显示“查看购买渠道”；缺少链接时不伪造入口。

结果顶部保留本次需求摘要。价格提示靠近金额展示，避免只在页面底部说明。

### 5.4 方案对比

- 对比维度优先体现用户关注点，而非堆满所有参数。
- 键盘展示配列、数字区、连接、轴体版本等；鼠标展示重量、尺寸、连接和功能等。
- 键鼠组合先对比总价，再分组比较键盘与鼠标。
- 未知参数显示“暂无资料”，不以默认值补齐。
- 在相同维度下标出匹配程度、依据与取舍；不生成没有定义的“综合评分 98 分”。

### 5.5 继续调整

用户可使用快捷操作或自然语言修改需求，如“预算降到 350”“必须蓝牙”“更看重游戏”。

更新前展示改变的条件，继承其余明确要求。只有用户主动确认更新后才重新生成。

上一版结果保留为历史快照；新请求失败时仍能查看。历史方案标明生成时间，其价格与当前资料有差异时提示重新核对。

## 6. 推荐业务规则

### 6.1 区分硬要求与偏好

| 类型 | 示例 | 推荐行为 |
|---|---|---|
| 硬要求 | 总价不超过 500 元、必须蓝牙、必须数字区 | 必须满足，证据不足时不得声称已满足 |
| 偏好 | 尽量安静、比较轻、偶尔游戏 | 影响排序与解释，可存在明确说明的取舍 |
| 未确定 | 对轴体不了解、还没想好布局 | 必要时追问，不擅自形成硬要求 |

“必须”“只要”等明确表达优先视为硬要求；“尽量”“希望”等优先视为偏好。语义存在明显歧义时由用户确认。

预算是商品参考价合计的硬上限。若用户明确要求“含运费的到手价”，但缺少可核对的费用信息，应说明无法确认，不能按商品标价冒充满足要求。

### 6.2 推荐流程

1. 理解需求，生成预算、品类、用途、硬要求和偏好的结构化记录。
2. 对关键缺失或冲突信息进行必要确认。
3. 从有效商品版本中筛选品类、兼容性、明确参数与价格条件。
4. 找到候选商品的证据和相关选购知识。
5. 计算单品或组合参考价，按明确规则选择方案。
6. 由 AI 解释匹配理由与取舍，并绑定依据。
7. 后端校验商品标识、版本、参数、引用与金额后再交付结果。

**AI 负责理解和表达；商品事实、金额计算与硬条件校验由数据和后端规则负责。**

### 6.3 排序与方案差异

[建议] 先确保硬要求满足，再考虑主要用途、用户偏好、资料完整性和价格利用情况。

- 不以“花满预算”作为默认目标；更便宜且已满足需求的商品可以优先。
- “更适合游戏”“更安静”等结论必须有相应参数或测试证据，不能仅靠营销词和模型常识。
- 对多用途用户，应解释方案偏向和代价。
- 多套方案应有与需求相关的实际差异，不能只更换颜色制造差异。
- 第一版排序权重为待评测的产品规则，不宣称已达到最优。

### 6.4 禁止生成的结论

- 商品库中不存在的型号、参数或版本。
- 没有来源的价格、折扣、库存与实测性能。
- 将不同版本的价格和特点拼成一件商品。
- 以未知信息证明满足硬要求。
- 将“可考虑”表达为确定的“最适合你”“全网最低价”。
- 自动调高预算、改变品类或放宽用户明确要求。

## 7. 商品资料与选购知识库

### 7.1 两类资料分别维护

| 资料 | 解决的问题 | 第一版组织方式 |
|---|---|---|
| 商品数据 | 哪些具体产品满足预算和参数条件 | 结构化数据，经校验后导入数据库 |
| 选购知识与证据 | 为什么这些条件重要、某结论有哪些依据 | 按主题组织文档，并关联商品与来源 |

预算与连接方式等精确条件优先使用字段筛选。语义检索用于发现相关知识，不替代金额、型号和硬条件校验。

模型自身记忆可以帮助理解表达，不能作为某件商品的已核实资料。

### 7.2 信息来源与采集方式

| 来源 | 获取内容 | 使用规则 |
|---|---|---|
| 厂商官网、规格表与说明书 | 基础参数、版本、兼容性 | 记录地区、具体版本和出处 |
| 对应地区的官方店铺或可信销售渠道 | 价格、购买链接、可售状态 | 独立记录价格条件与获取时间 |
| 有明确测试条件的评测或自身测试 | 噪声、延迟、体验观察等 | 标明测试方法和适用条件，保留差异 |
| 用户评价 | 使用问题和体验线索 | 后续按需引入，不直接当作客观性能事实 |

第一版采用“精选资料＋辅助提取＋核对入库”。后续优先使用可用 API、数据导出或允许访问的页面采集；爬虫是资料获取方式之一，不是推荐成立的依据。

采集只整理所需事实与必要证据摘要。原始资料保留出处；来源有访问限制时，不以绕过限制作为数据获取方案。

### 7.3 数据准备流程

**确定选品范围 → 收集来源 → 提取字段 → 统一名称和单位 → 检查版本与冲突 → 核对 → 发布到推荐库。**

AI 可以辅助提取字段，但不得自动把缺失数据补成已知值。自动采集结果先进入待核对状态；异常数据不直接覆盖正在使用的记录。

第一版建议覆盖约 20～30 款型号，横跨几个实际预算区间和用途。应检查键盘、鼠标分别有足够候选，并能组成多套有效组合；覆盖不足时说明资料库边界，不假装覆盖全部市场。

### 7.4 核心数据对象

| 对象 | 关键字段 | 设计目的 |
|---|---|---|
| 商品型号 | 商品标识、品类、品牌、型号、地区 | 区分商品身份 |
| 商品版本 | 版本标识、所属型号、轴体／规格、参数、核对状态 | 防止同名不同配置混用 |
| 渠道与价格记录 | 版本标识、渠道、链接、人民币参考价、价格条件、记录时间 | 支撑预算计算与价格追溯 |
| 来源与证据 | 来源链接、发布日期／核对时间、适用版本、支持的字段或判断、摘要 | 支撑推荐理由与冲突处理 |
| 选购知识 | 主题、适用品类、解释内容、关联来源、复核时间 | 支撑必要追问和参数解释 |
| 推荐需求 | 预算、品类、用途、硬要求、偏好、未确定项 | 保证多轮调整保持一致 |
| 推荐结果快照 | 需求快照、商品版本、价格记录、合计、理由、证据、生成时间 | 支撑对比、失败恢复与历史提示 |

上述为产品数据要求，数据库表结构与接口另行设计。

### 7.5 商品字段要求

- 通用：品牌、型号、具体版本、品类、连接方式、系统兼容、尺寸、重量和对应来源。
- 键盘：配列或按键数量、是否含数字区、轴体版本；热插拔等功能按已知资料记录。
- 鼠标：尺寸、重量、左右手适配、连接方式和关键按键功能。
- 性能与体验：存在相关资料时记录测试条件与结果；不存在时保留未知状态。
- 字段允许为空，但商品身份、具体版本与参数出处须可追溯；用于预算内推荐时还必须有有效参考价。
- 图片用于辅助识别商品，应对应具体产品，不把概念图展示为真实产品照片。

### 7.6 价格与新鲜度

[建议] 初期按 7 天作为参考价格的复核提醒阈值，后续根据维护能力与价格波动调整。该阈值是产品维护规则，不证明价格在此期间一定不变。

- 统一记录币种、渠道、具体版本、获取时间及适用条件。
- 优先记录无需特定身份或复杂条件的公开价格。
- 会员、新客、地区补贴、领券等条件价格不能作为无条件默认参考价。
- 结果始终显示“参考价”，并展示记录时间；不标注“实时价”。
- 缺价、过期或条件不清的价格，不用于生成声称确定预算内的方案。
- 全部候选价格失效时，可展示待核价候选与原因，但不能给出预算满足的确定结论。
- 参数与价格分开更新；一次价格变化不重写产品参数。

### 7.7 资料缺失与冲突

- 缺失字段显示“暂无资料”，不填写零值或自造标签。
- 冲突先检查型号、版本、地区、测试条件与日期是否一致。
- 冲突未解决时记录待核对状态，不用存在冲突的字段证明满足用户硬要求。
- 测试结论必须限定适用条件，不能无条件推广到其他版本或所有使用环境。
- 主观体验保留为体验依据；不把厂商宣传或单条评价转成独立实测结论。

### 7.8 知识检索的演进

第一版可以按品类、主题与关键词检索少量已审核文档。数据增长后，再评估语义检索与向量索引。

检索到的文段必须带来源和适用范围。AI 输出关键结论时应关联证据标识；后端只允许引用本次检索实际返回的资料。

第一版不要求训练或微调模型，不以引入向量数据库作为完成知识库的唯一标准。

## 8. 异常状态与恢复

| 状态 | 用户能看到什么 | 下一步 |
|---|---|---|
| 预算为空或无效 | 在预算输入处说明问题 | 修改预算后继续 |
| 需求互相冲突 | 展示冲突项，如“只要有线”和“必须蓝牙” | 选择最终要求 |
| 关键事实不足 | 说明尚不能判断的要求 | 补充信息或选择调整该要求 |
| 无商品匹配 | 说明未匹配的关键条件及资料库范围 | 调整预算／要求，或保留条件等待补充资料 |
| 只能匹配少量方案 | 按实际数量展示 | 查看方案或调整需求，不凑数 |
| 价格缺失或过期 | 标明待核价，避免预算满足结论 | 更新价格资料或选择其他有效候选 |
| 已核实渠道停售 | 显示渠道状态，退出该渠道的有效候选 | 使用其他可信渠道或商品 |
| 渠道可售状态未知 | 不承诺有货，提示到渠道核对 | 查看渠道信息 |
| AI 返回无效商品或引用 | 后端阻止展示错误方案 | 有限重试；失败后说明暂时无法完成 |
| 请求超时或服务失败 | 保留需求与上一版结果，说明失败 | 用户主动重试或修改需求 |
| 重复点击生成 | 显示正在处理，同一请求只执行一次 | 等待、取消或完成后继续 |

不能把“建议调高预算”直接执行成调高预算。无匹配时不以需求外商品冒充已满足条件的结果。

## 9. 系统职责与非功能要求

### 9.1 职责边界

| 部分 | 负责内容 |
|---|---|
| 前端 | 输入、确认、状态反馈、方案展示、对比和调整 |
| 后端 | 数据查询、金额计算、候选选择、版本与证据校验、调用控制 |
| AI | 理解需求、必要追问、根据提供资料解释推荐 |
| 数据维护 | 资料获取、核对、冲突处理、价格复核与候选覆盖 |

基础技术栈、pytest／Playwright 测试及 Docker Compose 部署方向已确认，技术方案见 [TECHNICAL.md](./TECHNICAL.md)。具体模型供应商、运行版本、生产环境和检索增强参数为 [待决策]。技术文档同时描述实际实现基线与演进方案。

### 9.2 第一版质量要求

- 桌面与手机浏览器都能完成输入、推荐和对比流程；移动端关键金额与按钮不得被遮挡。
- 生成过程有清晰反馈，失败可恢复；不得用未经确认的生成耗时承诺作为界面文案。
- 明确区分资料检索、推荐解释与错误状态，避免展示虚构的处理进度。
- 服务密钥留在服务端；用户提交内容不赋予模型修改商品库或执行购买的权限。
- 第一版不要求姓名、电话、地址等个人信息；保存需求原文与历史记录的方式应在实现前确定并向用户说明。
- 开发日志优先记录匿名请求标识、候选与证据标识、错误、耗时及调用成本，避免无必要地记录个人内容。
- 推荐生成应有重复请求控制与有限重试，用户修改尚未提交的输入不触发付费调用。
- 展示推荐资料的核对时间，方便定位数据变化造成的结果差异。

## 10. 评测与验收

### 10.1 验收用例

以下用例均须使用可核对的固定资料，并保留需求、候选、结果和核验记录。

| 编号 | 测试场景 | 必须达到的行为 |
|---|---|---|
| AC-01 | 预算明确的键盘推荐 | 推荐为有效键盘版本，参考价不超预算 |
| AC-02 | 预算明确的鼠标推荐 | 推荐为有效鼠标版本，解释实际相关参数 |
| AC-03 | 500 元键鼠组合 | 同时包含键盘与鼠标，合计由后端计算且不超过 500 元 |
| AC-04 | 必须蓝牙 | 所有匹配方案有已核实的蓝牙支持；未知不能当作满足 |
| AC-05 | 必须数字区 | 候选键盘具有已核实数字区，或明确返回无匹配 |
| AC-06 | 宿舍使用，希望安静 | 说明噪声证据与限制，不把轴体名称直接当作实测证明 |
| AC-07 | 将预算从 500 改为 350 | 新结果按 350 计算，未修改要求保留，旧结果仍可查看 |
| AC-08 | 预算内没有匹配 | 明确原因并允许用户调整，不自动超预算 |
| AC-09 | 同型号不同版本 | 价格、参数与证据全部对应本次具体版本 |
| AC-10 | 价格失效或缺失 | 不声称确定满足预算，展示核价状态或其他候选 |
| AC-11 | AI 编造商品、参数或引用 | 校验拒绝错误结果，未核实内容不进入正式推荐卡片 |
| AC-12 | 只有一套匹配 | 只展示一套，不复制或放宽条件凑足三套 |
| AC-13 | 生成失败、超时与重复点击 | 需求与旧结果保留，可主动重试，重复操作不重复执行 |
| AC-14 | 无资料支持的体验要求 | 标明无法确认，必要时追问或返回无法判断 |
| AC-15 | 表单与自由描述冲突 | 用户确认后再筛选，不静默改变条件 |
| AC-16 | 手机浏览推荐与对比 | 商品、金额、来源及核心操作可读可用 |

第一版建议准备至少 20 条选购评测需求，覆盖单品、组合、多用途、预算边界、追问、无匹配、缺资料和多轮调整。

测试中的硬条件违反、金额错误、无效商品和虚构引用均属于阻断交付的问题。固定用例通过只证明该批用例达标，不能推广为全市场或全部需求正确。

### 10.2 评估指标

| 指标 | 记录方式 | 用途 |
|---|---|---|
| 预算与硬条件符合率 | 符合要求的有效方案数／参与评测的有效方案数 | 检查规则执行 |
| 事实错误与虚构引用 | 逐条核对产品版本、字段与引用 | 检查资料可靠性 |
| 推荐理由有据比例 | 有实际关联证据的可核实结论数／该类结论总数 | 检查解释质量 |
| 场景覆盖情况 | 统计各预算、品类和用途的可用候选与无匹配情况 | 指导资料扩充 |
| 用户任务完成情况 | 观察是否能理解方案、比较并选出倾向方案 | 验证实际选购帮助 |
| 耗时与调用成本 | 记录单次请求与多轮流程的实测数据 | 指导工程优化 |

上述指标尚未测量。除验收中的阻断问题外，其余目标值在取得第一轮基线后确定，不编造达成数据。

## 11. 开发与数据准备顺序

| 里程碑 | 交付内容 | 进入下一阶段的条件 |
|---|---|---|
| M0 · 需求与资料样本 | 本文档、字段规范、一小批核对后的商品及选购知识 | 单品与组合有可验证候选，关键规则清楚 |
| M1 · 可体验的推荐原型 | 需求输入、确认、结果、对比与调整页面；明确标注的演示数据 | 用户能走完选购流程，页面不假装接入实时数据 |
| M2 · 数据与推荐链路 | 正式资料导入、筛选、金额计算、来源展示与异常处理 | 有效候选、金额和出处可追溯 |
| M3 · 真实 AI 推荐 | 需求理解、追问、解释、多轮调整、服务失败恢复 | AI 输出通过事实与规则校验 |
| M4 · 第一版验收 | 固定用例、场景评测、实际浏览器流程核验和问题修复 | P0 完成，阻断问题解决，真实完成边界明确 |

M1 的演示数据用于验证交互，不作为真实商品推荐发布。前端搭建、数据准备与规则设计可以协调推进，但不能以页面展示成功代表真实推荐服务已完成。

## 12. 长期演进蓝图

### 阶段一：键盘与鼠标推荐助手

完成本文 P0，建立精选资料库，先证明预算与用途驱动的推荐有效。

### 阶段二：资料维护与推荐能力增强

加入更便捷的数据管理、可用来源的自动更新、资料变化检查、收藏与分享。根据实际需求扩展选购知识和检索能力。

### 阶段三：扩展电子产品品类

按真实使用反馈扩展耳机、显示器等品类。每新增品类先定义字段、适用场景与证据要求，不直接套用键鼠规则。

### 阶段四：加入商城

在推荐体验与数据稳定后，引入账号、购物车、订单与支付流程。渠道参考价格与商城销售价格分别管理；真实库存、订单金额与交易状态以商城后端为准。

支付、发货和售后另行设计需求与验收。推荐助手第一版不承担这些交易能力。
